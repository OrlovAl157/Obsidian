# 🔌 DIP — принцип инверсии зависимостей

> Модули должны зависеть от абстракций, а не от конкретных деталей реализации. Верхний уровень не знает, какой именно нижний уровень ему достался.

## Справка

| Уровень | Что содержит | Пример |
| --- | --- | --- |
| Верхний | бизнес-логика: **что** должна делать система | авторизация, отправка уведомлений, валидация операций |
| Нижний | детали реализации: **как** именно это делается | подключение к конкретной БД |

| Формулировка принципа | Смысл |
| --- | --- |
| верхний уровень не зависит от нижнего | оба зависят от абстракций |
| абстракции не зависят от деталей | детали зависят от абстракций |

| Нарушение | Исправление |
| --- | --- |
| `Switch` сам создаёт `LightBulb()` | `Switch` принимает `Switchable` |
| `Auth` создаёт `SQLiteConnection()` | `Auth` принимает `DBConnection` |
| `Auth(connection: SQLiteConnection)` — абстракция есть, но не используется | `Auth(connection: DBConnection)` |

## 🧠 Суть принципа

Система обычно состоит из модулей двух уровней:

- **нижний** — базовая функциональность (например, подключение к БД); содержит детали, которые меняются в зависимости от БД
- **верхний** — бизнес-логика; определяет, что должна выполнять система, не вдаваясь в детали

```
было:                              стало:
 Switch ──────► LightBulb           Switch ──────► Switchable (абстракция)
 (верх)         (низ)                                   ▲        ▲
                                                        │        │
                                                   LightBulb    Fan
```

Зависимость «инвертируется»: теперь не верх зависит от низа, а **низ реализует абстракцию**, которую задал верх.

## 💡 Пример 1 — выключатель и лампочка

**Исходный код.** Выключатель работает только с лампочкой:

```python
class LightBulb:
    def turn_on(self):
        print('Включение лампочки')

    def turn_off(self):
        print('Выключение лампочки')


class Switch:
    def __init__(self):
        self.lightbulb = LightBulb()

    def process(self):
        self.lightbulb.turn_on()
```

Чтобы управлять вентилятором, придётся менять логику `Switch`: он зависит от модуля нижнего уровня. Каждое новое устройство — снова правка, а значит, ещё и нарушение OCP — [[02 — 🔓 OCP — принцип открытости и закрытости]].

**Шаг 1.** Выделяем абстракцию:

```python
from abc import ABC, abstractmethod


class Switchable(ABC):
    @abstractmethod
    def turn_on(self):
        pass

    @abstractmethod
    def turn_off(self):
        pass
```

**Шаг 2.** Детали зависят от абстракции — наследуют её и реализуют методы:

```python
class LightBulb(Switchable):
    def turn_on(self):
        print('Включение лампочки')

    def turn_off(self):
        print('Выключение лампочки')


class Fan(Switchable):
    def turn_on(self):
        print('Включение вентилятора')

    def turn_off(self):
        print('Выключение вентилятора')
```

**Шаг 3.** Выключатель зависит от абстракции:

```python
class Switch:
    def __init__(self, device: Switchable):
        self.device = device

    def process(self):
        self.device.turn_on()
```

```python
Switch(LightBulb()).process()
# → Включение лампочки

Switch(Fan()).process()
# → Включение вентилятора
```

Для нового устройства достаточно создать новый класс-наследник `Switchable`, не меняя существующие. Связь между модулями ослаблена, код меньше подвержен ошибкам и лучше масштабируется.

## 🗄 Пример 2 — Auth и база данных

**Нарушение.** `Auth` (верхний уровень) жёстко завязан на `SQLiteConnection` (нижний):

```python
class SQLiteConnection:
    def connect(self):
        """Подключение к БД"""


class Auth:
    def __init__(self, connection):
        self.connection = SQLiteConnection()      # зависимость создаётся внутри

    def auth(self):
        """Аутентификация пользователя"""
```

При добавлении новой БД придётся менять `Auth`.

**Исправление.** Снова применяем абстракцию:

```python
from abc import ABC, abstractmethod


class DBConnection(ABC):
    @abstractmethod
    def connect(self):
        pass


class SQLiteConnection(DBConnection):
    def connect(self):
        """Подключение к БД"""


class MySQLConnection(DBConnection):
    def connect(self):
        """Подключение к БД"""


class Auth:
    def __init__(self, connection: DBConnection):
        self.connection = connection

    def auth(self):
        """Аутентификация пользователя"""
```

Исправленный вариант удовлетворяет сразу трём принципам: DIP, OCP и LSP — [[03 — 🔄 LSP — принцип подстановки Лисков]]. Одну БД легко заменить другой, и код `Auth` при этом не меняется.

## 🪤 Ловушка — абстракция есть, а зависимость нет

Наличие абстракции не гарантирует соблюдения принципа:

```python
class DBConnection(ABC):
    @abstractmethod
    def connect(self):
        pass


class SQLiteConnection(DBConnection):
    def connect(self):
        """Подключение к БД"""


class Auth:
    def __init__(self, connection: SQLiteConnection):    # ❌ ожидается конкретный тип
        self.connection = connection
```

Абстрактный `DBConnection` существует, но `Auth` ожидает именно `SQLiteConnection`. Принцип нарушен: если понадобится другой тип соединения, возможно, придётся править `Auth`. Зависимость должна быть от абстракции (`DBConnection`), а не от детали.

## 💉 Инъекция зависимостей

**Инъекция зависимостей** (Dependency Injection, DI) — паттерн проектирования, при котором объект получает нужные ему другие объекты (зависимости) **извне**, а не создаёт их сам.

```python
# ❌ создаёт зависимость сам
class Auth:
    def __init__(self):
        self.connection = SQLiteConnection()

# ✅ получает зависимость снаружи
class Auth:
    def __init__(self, connection: DBConnection):
        self.connection = connection

auth = Auth(MySQLConnection())      # решение о том, какую БД брать, принято снаружи
```

Именно DI позволяет соблюдать принцип инверсии зависимостей на практике.

## 🚩 Как заметить нарушение

| Признак в коде | Что это значит |
| --- | --- |
| `self.x = ConcreteClass()` внутри `__init__` | класс сам создаёт свою зависимость |
| в аннотации параметра — конкретный класс | зависимость от детали, а не от абстракции |
| замена одной реализации требует правки класса-пользователя | верхний уровень привязан к нижнему |

## 💡 Практические замечания

- DIP и OCP похожи, но решают разные уровни одной проблемы: OCP защищает код от правок при расширении, DIP уменьшает связанность между модулями
- Абстракцию в Python обычно задают через `ABC` — [[01 — 🔒 Абстрактные классы (abc)]]; для лёгких случаев подойдёт `typing.Protocol` — [[04 — 🔗 Протоколы, Sequence и Callable]] (это дополнение, в исходных примерах его нет)
- Не вводи абстракцию, если реализация точно одна и менять её не придётся — см. предупреждение в [[00 — 🧱 SOLID — обзор]]

## ⚠️ Частые ошибки

**❌ Создавать зависимость внутри класса:**
```python
self.connection = SQLiteConnection()     # ❌ жёсткая связь
```

**❌ Аннотировать параметр конкретным типом при наличии абстракции:**
```python
def __init__(self, connection: SQLiteConnection):   # ❌
def __init__(self, connection: DBConnection):       # ✅
```

**❌ Принимать параметр, но не использовать его:**
```python
def __init__(self, connection):
    self.connection = SQLiteConnection()   # ❌ параметр проигнорирован
```

**❌ Считать «есть ABC — значит DIP соблюдён».** Нужно, чтобы **верхний уровень** тоже зависел от абстракции.

---

## ✅ Главные правила

✅ Верхний уровень не зависит от нижнего — оба зависят от абстракций  
✅ Детали зависят от абстракций, а не наоборот  
✅ Зависимости передаются снаружи (DI), а не создаются внутри  
✅ В аннотациях — абстракция (`DBConnection`), а не реализация (`SQLiteConnection`)  
✅ DIP работает вместе с OCP и LSP: исправленный код обычно удовлетворяет всем трём
