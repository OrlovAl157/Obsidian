# 🎯 SRP — принцип единственной ответственности

> Каждый модуль должен иметь только одну причину для изменения. «Одна ответственность» — это не «одна задача», а «один актор»: одна группа источников требований.

## Справка

| Понятие | Значение |
| --- | --- |
| Модуль | связанный набор функций и структур данных; например, класс или модуль Python |
| Причина для изменения | изменение требований к приложению, из-за которого приходится менять код |
| Актор | роль, которую играет группа источников требований по отношению к приложению |
| Нарушение SRP | один класс обслуживает нескольких акторов |
| Решение | разнести код по классам: один класс — один актор |

| Нарушение | Исправление |
| --- | --- |
| `BankAccount` с историей, отчётами и валидацией | `BankAccount`, `History`, `Report`, `Validator` |
| `FileManager` с файлами и архивами | `TextFileManager`, `ZipFileManager` |

---

## 🧠 Суть принципа

Программа неизбежно меняется, чтобы удовлетворять разные источники требований. Каждый такой источник — потенциальная причина для изменения кода.

```
несколько источников  ─┐
требований            ─┼─►  одна группа = актор  ─►  один модуль на актора
(пользователь, бизнес) ┘
```

Одного и того же изменения могут хотеть сразу несколько источников, поэтому говорят не о каждом по отдельности, а о **группе** — акторе.

> ⚠️ Принцип считается самым трудным для понимания: из-за названия новички думают, что каждый модуль должен выполнять **какую-то одну задачу**. Это неверно.

---

## 🎭 Что такое актор

Актор — роль группы источников требований. Акторами бывают:

- пользователи приложения
- бизнес-процессы
- внутренние и внешние сервисы
- другие модули и любые другие источники требований, не связанные с текущим модулем

Для приложения онлайн-банка:

| Актор | Что ему нужно |
| --- | --- |
| Вкладчик | история своих операций по счёту |
| Бухгалтер | выгрузка отчёта в разных форматах |
| Администратор безопасности | предотвращение мошенничества, например подтверждение операций выше определённой суммы |

Функции, которые отвечают за разных акторов, должны жить в разных модулях.

## 🏦 Пример 1 — BankAccount

**Нарушение:**

```python
class BankAccount:
    def __init__(self, user_id):
        self.user_id = user_id

    def view_history(self):
        """Получение истории операций."""       # вкладчик

    def generate_report(self):
        """Формирование отчёта."""              # бухгалтер

    def validate_operation(self):
        """Подтверждение операции."""           # администратор безопасности
```

Класс объединяет трёх акторов, а значит, у него три причины для изменения:

- изменился формат отчёта → правим класс
- изменился способ валидации → снова правим тот же класс

Хуже того, если методы используют общий код (например, проверку прав доступа), то изменение политики безопасности заденет всех трёх акторов. Для некоторых из них это будет избыточно или сломает их логику, и придётся править и их код.

**Исправление** — по одному классу на актора:

```python
class BankAccount:
    def __init__(self, user_id):
        self.user_id = user_id


class History:
    def view_history(self, account):
        """Получение истории операций."""


class Report:
    def generate_report(self, account):
        """Формирование отчёта."""


class Validator:
    def validate_operation(self, account):
        """Подтверждение операции."""
```

Теперь четыре небольших класса: ими проще управлять, их легче тестировать и отлаживать.

## 📁 Пример 2 — FileManager

**Нарушение:**

```python
class FileManager:
    def __init__(self, filename):
        self.path = filename

    def read(self):
        """Чтение из файла."""

    def write(self):
        """Запись в файл."""

    def compress(self):
        """Упаковка архива."""

    def decompress(self):
        """Распаковка архива."""
```

Здесь два актора:

- `read()` и `write()` — пользователь или подсистема, работающая с файлами
- `compress()` и `decompress()` — пользователь или подсистема, работающая с архивами

С ростом требований класс начнёт обрастать обработкой изображений, видео и других форматов и станет отвечать за слишком многое.

**Исправление:**

```python
class TextFileManager:
    def __init__(self, filename):
        self.path = filename

    def read(self):
        """Чтение из файла."""

    def write(self):
        """Запись в файл."""


class ZipFileManager:
    def __init__(self, filename):
        self.path = filename

    def compress(self):
        """Упаковка архива."""

    def decompress(self):
        """Распаковка архива."""
```

В каждом классе по два метода — и это нормально: у обоих одна причина для изменения. `TextFileManager` меняется из-за требований к текстовым файлам, `ZipFileManager` — из-за требований к архивам.

## 👹 Божественный объект

Объект, у которого слишком много ответственностей, называют **божественным объектом** (God object). Это антипаттерн: он знает и делает всё, его трудно понять, тестировать и менять. SRP — способ его избежать.

---

## 💡 Практические замечания

- Одна ответственность связана не с количеством методов, а с основной задачей класса. **Если несколько разных методов имеют одну причину для изменения, их нужно держать в одном классе**
- Акторов не всегда можно выделить однозначно. В примере с файловым менеджером чтение и запись можно считать разными акторами, и тогда разделение будет другим
- Ответ зависит от задачи: один и тот же код при разных требованиях даёт разное число акторов

## ⚠️ Частые ошибки

**❌ Читать принцип как «один класс — один метод» или «одна задача».**
```python
class OrderPrinter:
    def print_header(self): ...
    def print_items(self): ...
    def print_footer(self): ...
# три метода — но одна причина для изменения (формат печати заказа). Это нормально.
```

**❌ Дробить код, не опираясь на акторов.** Если разнести по классам методы с одной причиной для изменения, вместо одной правки потребуется несколько.

**❌ Оставлять «удобный» общий метод между разными акторами.** Именно общий код становится источником конфликтов: правка для одного актора неожиданно ломает другого.

**❌ Складывать всё в один «менеджер».** Классы с именами `Manager`, `Helper`, `Utils`, которые растут бесконечно, — частый признак божественного объекта.

---

## ✅ Главные правила

✅ У модуля — одна причина для изменения  
✅ Причина для изменения связана с актором — группой источников требований  
✅ Методы для разных акторов — в разных классах  
✅ Методы с одной причиной для изменения — в одном классе, даже если их много  
✅ Божественный объект — антипаттерн, SRP помогает его избежать  
✅ Акторов не всегда можно определить однозначно — смотри на задачу
