# 🔄 LSP — принцип подстановки Лисков

> Объекты дочерних классов должны без изменений в работе программы использоваться везде, где ожидается объект родительского класса. Наследование не должно нарушать контракт родителя.

## Справка

| Правило контракта | Что запрещено в наследнике |
| --- | --- |
| Предусловия | **усиливать** — требовать от вызывающего больше, чем родитель |
| Постусловия | **ослаблять** — гарантировать меньше, чем родитель |
| Инварианты | нарушать — свойства объекта, которые должны сохраняться всегда |

| Нарушение контракта | Пример |
| --- | --- |
| новое исключение | наследник бросает ошибку там, где родитель работал |
| ухудшение гарантий результата | гарантия 6 месяцев вместо года |
| несовместимый тип результата | родитель возвращает число, наследник — строку |
| изменение поведения метода | `Square` меняет обе стороны вместо одной |

| Решение | Когда |
| --- | --- |
| общая абстракция вместо наследования друг от друга | `Rectangle` и `Square` от `Shape` |
| композиция вместо наследования | `StrictLogger` использует `Logger`, а не наследуется от него |

## 🧠 Суть принципа

Любой код, работающий с объектом класса, должен так же корректно работать с объектами его дочерних классов — причём **не зная**, какой именно объект ему достался.

```
def process(logger: Logger): ...

process(Logger())        ✅
process(SubLogger())     ✅  должно работать так же, без «но»
```

Принцип близок к методологии контрактного программирования и ведёт к двум ограничениям на то, как контракты взаимодействуют с наследованием:

- предусловия не могут быть усилены в подклассе
- постусловия не могут быть ослаблены в подклассе

Простыми словами: **дочерний класс не должен усложнять входные требования и упрощать выходные результаты**.

---

## 📜 Контракты — пред- и постусловия

Пример маркетплейса: покупка товара требует подтверждения возраста.

**Предусловие** — что нужно предоставить на входе:

| Родитель требует | Наследник требует | Нарушение? |
| --- | --- | --- |
| любой документ | только паспорт или права | ❌ да, требования ужесточены |
| паспорт | паспорт или права | ✅ нет, требования смягчены |

**Постусловие** — что гарантируется на выходе (например, гарантия на товар):

| Родитель даёт | Наследник даёт | Нарушение? |
| --- | --- | --- |
| 1 год | 1 год и больше | ✅ нет, гарантия не хуже |
| 1 год | меньше года | ❌ да, гарантия ухудшена |

Правило запомнить легко: наследник должен соблюдать требования родителя **или делать их проще**, а гарантии давать **не хуже** родительских.

## 🔒 Инварианты

Принцип относится именно к **поведению** методов. Любое отклонение в поведении его нарушает: новые исключения, ухудшение гарантий результата, возврат несовместимых типов данных.

Дочерние классы обязаны сохранять **инварианты** — свойства объекта, которые остаются неизменными на протяжении всего времени его существования независимо от конкретной реализации.

## 🟦 Пример 1 — Rectangle и Square

**Исходный код.** Наследуем квадрат от прямоугольника:

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def set_width(self, width):
        self.width = width

    def set_height(self, height):
        self.height = height

    def area(self):
        return self.width * self.height


class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side)

    def set_width(self, width):
        self.width = self.height = width

    def set_height(self, height):
        self.height = self.width = height
```

С математической точки зрения квадрат — частный случай прямоугольника, и наследование выглядит логичным. Но принцип подстановки нарушен: у `Square` изменение одной стороны меняет и другую, то есть ослаблено постусловие родителя — вторая сторона должна оставаться неизменной.

**Как это ломается на практике:**

```python
def resize(rect: Rectangle):
    rect.set_width(5)
    rect.set_height(10)
    assert rect.area() == 50       # ожидание для любого Rectangle

resize(Rectangle(1, 1))            # ✅ 5 * 10 = 50
resize(Square(1))                  # ❌ AssertionError: у квадрата area() == 100
```

Проблема в неверно выбранной модели наследования: с геометрической точки зрения квадрат — частный случай прямоугольника, но интерфейсы с точки зрения **поведения** несовместимы.

**Исправление.** Убираем зависимость классов друг от друга и выносим общее поведение в абстракцию:

```python
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self):
        pass


class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def set_width(self, width):                         # индивидуальный контракт
        self.width = width

    def set_height(self, height):                       # индивидуальный контракт
        self.height = height

    def area(self):                                     # общий контракт
        return self.width * self.height


class Square(Shape):
    def __init__(self, side):
        self.side = side

    def set_side(self, side):                           # индивидуальный контракт
        self.side = side

    def area(self):                                     # общий контракт
        return self.side * self.side
```

`Shape` легко заменить на `Rectangle` или `Square`: оба реализуют его интерфейс и соблюдают общий контракт. Наборы атрибутов и методов разные, но `area()` есть у обоих и всегда возвращает площадь.

```python
def total_area(shapes):
    return sum(shape.area() for shape in shapes)


shapes = [Rectangle(10, 20), Square(10)]
print(total_area(shapes))
# → 300
```

Функции `total_area()` неважен тип фигуры — важно, что она реализует нужный интерфейс и соблюдает общий контракт. В этом и суть принципа.

## 📝 Пример 2 — Logger и StrictLogger

**Исходный код:**

```python
class Logger:
    def log(self, message):
        print(message)


class StrictLogger(Logger):
    def __init__(self, level):
        self.level = level

    def log(self, message, level):
        if level < self.level:
            raise ValueError(f'Можно записывать события не ниже уровня {self.level}')
        super().log(message)
```

`StrictLogger` усиливает предусловие: `Logger` записывает любые события, а `StrictLogger` — только определённого уровня (плюс требует лишний аргумент `level`). Подставить его вместо `Logger` без возможных ошибок не получится.

Наследование даже от общего абстрактного класса тут не поможет: у `StrictLogger` свой, более жёсткий контракт.

**Исправление — композиция вместо наследования:**

```python
class Logger:
    def log(self, message):
        print(message)


class StrictLogger:
    def __init__(self, logger, level):
        self.logger = logger
        self.level = level

    def log(self, message, level):
        if level < self.level:
            raise ValueError(f'Можно записывать события не ниже уровня {self.level}')
        self.logger.log(message)
```

`StrictLogger` получает объект `Logger` и **делегирует** ему запись. Он больше не разновидность `Logger`, а только использует его, поэтому не обязан соблюдать его контракт и может ставить собственные требования к `log()`.

## 💡 Практические замечания

- Если логичное «в реальной жизни» наследование ломает поведение (квадрат — прямоугольник), смотри на **контракт методов**, а не на отношения в предметной области
- Когда наследник вынужден усиливать требования родителя, обычно нужна композиция — [[07 — 🧩 Композиция]]
- Общую часть поведения выделяют в абстракцию, а различия оставляют в конкретных классах — [[01 — 🔒 Абстрактные классы (abc)]]
- Принцип сформулировала Барбара Лисков в 1987 году; она лауреат премии Тьюринга 2008 года

## ⚠️ Частые ошибки

**❌ Наследовать «по смыслу», не проверив контракт:**
```python
class Square(Rectangle): ...      # ❌ set_width ломает ожидание от Rectangle
```

**❌ Бросать в наследнике исключение там, где родитель работал:**
```python
class ReadOnlyList(list):
    def append(self, item):
        raise TypeError("нельзя")  # ❌ код, ожидающий list, сломается
```

**❌ Менять тип возвращаемого значения:**
```python
class Parent:
    def get_id(self): return 5          # int
class Child(Parent):
    def get_id(self): return "5"        # ❌ несовместимый тип
```

**❌ Добавлять обязательные параметры в переопределённый метод:**
```python
log(message)             # родитель
log(message, level)      # ❌ наследник требует больше
```

## ✅ Главные правила

✅ Наследника можно подставить вместо родителя без изменений в работе кода  
✅ Предусловия в наследнике не усиливать, постусловия — не ослаблять  
✅ Не бросать новых исключений, не ухудшать гарантии, не менять тип результата  
✅ Сохранять инварианты родителя  
✅ Если контракты несовместимы — общая абстракция или композиция вместо наследования  
✅ Смотреть на поведение методов, а не на «логичность» иерархии
