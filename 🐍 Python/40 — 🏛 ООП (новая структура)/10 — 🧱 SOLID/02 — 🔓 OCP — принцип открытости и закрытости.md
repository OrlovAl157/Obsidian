# 🔓 OCP — принцип открытости и закрытости

> Программные модули должны быть открыты для расширения, но закрыты для изменения: новый функционал добавляется новым кодом, а существующий не правится.

## Справка

| Часть формулировки | Что значит |
| --- | --- |
| Открыт для расширения | функциональность расширяется созданием **новых** модулей |
| Закрыт для изменения | расширение одного модуля не требует правок в модулях, которые его используют |

| Значение принципа | Автор | Суть |
| --- | --- | --- |
| Принцип Мейера | Бертран Мейер, 1988 | реализованный модуль не меняют (кроме исправления ошибок), расширяют наследованием |
| Полиморфный принцип | — | интерфейс остаётся неизменным, новые реализации ему полностью соответствуют |

| Нарушение | Решение |
| --- | --- |
| `if isinstance(shape, Circle)` в `Calculator` | абстрактный `Shape` с методом `area()`, каждая фигура считает площадь сама |
| `if type == "email" ... elif "sms"` в сервисе | абстрактный `NotificationChannel` с методом `send()` |

## 🧠 Суть принципа

Нарушение OCP проявляется, когда изменение в одном модуле заставляет менять другие, связанные с ним.

Например, если для нового типа уведомления нужно править модуль отправки, то это нарушение OCP. Заодно нарушается и SRP — [[01 — 🎯 SRP — принцип единственной ответственности]]: весь код, меняющийся по одной причине, должен находиться в одном модуле.

```
было:   новая фигура  ──►  правим Calculator  ──►  правим тесты  ──►  риск сломать старое
стало:  новая фигура  ──►  новый класс-наследник Shape  ──►  Calculator не тронут
```

---

## 📜 Два значения принципа

**Принцип Мейера** (1988). Однажды реализованный функционал модуля не должен модифицироваться, исключение — исправление ошибок. Новое поведение добавляют, создавая **новый модуль, который наследует поведение исходного и расширяет его**.

**Полиморфный принцип.** Основан на строгой реализации интерфейсов, наследовании от абстрактных базовых классов и полиморфизме. Исходный интерфейс остаётся неизменным, новые версии ему полностью соответствуют, но могут предлагать и новые функции.

> 💡 В программировании интерфейс и абстракция — разные вещи: интерфейс задаёт методы, которые нужно реализовать, а абстракция может содержать ещё и поведение. В Python жёсткого разделения нет, поэтому оба понятия используют в общем контексте — см. [[01 — 🔒 Абстрактные классы (abc)]].

## 📐 Пример 1 — Calculator и фигуры

**Исходный код:**

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height


class Calculator:
    @staticmethod
    def area(shape):
        return shape.width * shape.height
```

**Нарушение.** Чтобы добавить круг, придётся менять `Calculator`:

```python
from math import pi


class Circle:                                           # новая фигура
    def __init__(self, radius):
        self.radius = radius


class Calculator:
    @staticmethod
    def area(shape):
        if isinstance(shape, Circle):                   # правка действующего кода
            return pi * shape.radius * shape.radius
        return shape.width * shape.height
```

С каждой новой фигурой правки повторяются. Растёт хрупкость кода, усложняются поддержка и тестирование, появляется жёсткая зависимость между `Calculator` и классами фигур.

**Исправление.** Ответственность за вычисление площади делегируем самим фигурам. Для этого выделяем абстрактный класс `Shape`:

```python
from math import pi
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self):
        pass


class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return pi * self.radius * self.radius


class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height
```

Теперь `Shape` закрыт для изменений, но открыт для расширения: новая фигура — это новый класс-наследник.

## 🔔 Пример 2 — NotificationService

**Нарушение:**

```python
class NotificationService:
    def send_notification(self, notification_type, message, recipient):
        if notification_type == "email":
            self._send_email(message, recipient)
        elif notification_type == "sms":
            self._send_sms(message, recipient)
        elif notification_type == "push":
            self._send_push(message, recipient)

    def _send_email(self, message, recipient):
        """Отправка уведомления по email"""

    def _send_sms(self, message, recipient):
        """Отправка уведомления по sms"""

    def _send_push(self, message, recipient):
        """Отправка push-уведомления"""
```

Новый тип уведомления — ещё одно условие в `send_notification()`. Страдают стабильность, поддержка, тестирование и читаемость.

**Исправление.** Вместо одного класса на все типы создаём по классу на каждый тип и делегируем им отправку:

```python
from abc import ABC, abstractmethod


class NotificationChannel(ABC):
    @abstractmethod
    def send(self, message, recipient):
        pass


class EmailChannel(NotificationChannel):
    def send(self, message, recipient):
        """Отправка уведомления по email"""


class SMSChannel(NotificationChannel):
    def send(self, message, recipient):
        """Отправка уведомления по sms"""


class PushChannel(NotificationChannel):
    def send(self, message, recipient):
        """Отправка push-уведомления"""


class NotificationService:
    @staticmethod
    def send_notification(channel, message, recipient):
        channel.send(message, recipient)
```

`send_notification()` теперь принимает не тип уведомления, а **объект канала**, и благодаря полиморфизму вызывает его `send()`. Новый канал — это новый класс, а `NotificationService` остаётся нетронутым.

## 🚩 Как заметить нарушение

Принцип нарушается, когда поведение системы зависит от проверки конкретных типов данных, а не от полиморфного взаимодействия с объектами через единый интерфейс.

| Признак в коде | Что это значит |
| --- | --- |
| цепочка `if`/`elif` по типу или строковому коду | новый вариант = правка этой цепочки |
| `isinstance(obj, ...)` для выбора поведения | вызывающий код знает про конкретные классы |
| добавление нового случая требует правки уже работающего модуля | модуль не закрыт для изменения |

## 💡 Практические замечания

- Основной механизм решения — абстрактный класс + полиморфизм: вызывающий код работает с интерфейсом и не знает о конкретных классах — [[06 — 🎭 Полиморфизм]]
- OCP и DIP похожи, но защищают от разного: OCP — от изменения кода при расширении, DIP — от жёсткой связи между модулями. Подробнее — [[05 — 🔌 DIP — принцип инверсии зависимостей]]
- Принцип Мейера опирается на наследование, полиморфный вариант — на интерфейсы и абстрактные классы

## ⚠️ Частые ошибки

**❌ Оставлять `if isinstance(...)` в коде, который должен быть расширяемым:**
```python
if isinstance(shape, Circle):      # ❌ каждая новая фигура — правка здесь
    ...
shape.area()                        # ✅ каждая фигура знает, как считать себя
```

**❌ Создавать абстракцию «на будущее», хотя вариант всего один.** Вторая реализация может никогда не появиться — абстракция тогда только усложняет код.

**❌ Менять интерфейс абстракции вместо добавления нового класса.** Исходный интерфейс должен оставаться неизменным, иначе придётся править все реализации.

**❌ Делегировать, но оставить выбор класса в старом месте через `if`.** Нужно, чтобы вызывающий код получал уже готовый объект (канал, фигуру), а не решал, какой создать.

## ✅ Главные правила

✅ Новый функционал — новым классом, а не правкой существующего  
✅ Общий интерфейс — через абстрактный базовый класс  
✅ Выбор поведения — полиморфизмом, а не `if` по типу  
✅ Нарушение OCP обычно означает и нарушение SRP  
✅ Исходный интерфейс остаётся неизменным, расширяются реализации
