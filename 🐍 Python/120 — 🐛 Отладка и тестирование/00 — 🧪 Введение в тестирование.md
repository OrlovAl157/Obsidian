# 🧪 Введение в тестирование

## 📌 Коротко

> Тестирование — проверка того, что реальное поведение программы соответствует ожидаемому, на конечном наборе тестовых случаев. Юнит-тестирование — низкоуровневый вид тестирования, при котором проверяются отдельные единицы кода (функции, методы, классы) изолированно друг от друга.

---

## 🚀 Быстрая справка

| Тип тестового случая | Что это | Пример для `sum_a_b(a, b)` (только положительные целые) |
|---|---|---|
| **Обычный** | любое корректное значение, кроме крайних | `sum_a_b(5, 10)` |
| **Граничный** | минимально/максимально допустимое значение | `sum_a_b(1, 1)` — единица минимальна |
| **Некорректный** | значение, которое единица не должна обрабатывать | `sum_a_b(-1, 3)`, `sum_a_b(2.5, 1)` |

| Понятие | Суть |
|---|---|
| **Юнит-тестирование** | тестирование отдельных изолированных единиц кода |
| **Белый ящик** | тестировщик знает внутреннее устройство кода (юнит-тесты — это белый ящик) |
| **Чёрный ящик** | тестировщик знает только вход/выход, без деталей реализации |
| **TDD** | сначала пишутся тесты, потом код, который должен их пройти |

## 📖 Основное

### Зачем нужно тестирование

Ошибки в коде — это нормально, полностью избежать их невозможно. Задача тестирования — обнаружить как можно больше ошибок **до того**, как их найдёт пользователь. Тестирование не доказывает отсутствие ошибок — оно лишь демонстрирует их наличие (если тесты прошли, это не значит, что кода без багов, значит лишь, что эти конкретные тесты не нашли проблему).

### Этапы тестирования

1. **Анализ и проработка требований** — изучение того, что должно делать приложение, выявление рисков и неясностей, при необходимости — уточнение у заинтересованных сторон.
2. **Планирование тестирования** — определение целей, стратегии, сценариев и инструментов тестирования, распределение задач и сроков внутри команды.
3. **Разработка тестовых данных** — написание конкретных тестовых сценариев с входными и ожидаемыми выходными значениями.
4. **Настройка тестовой среды** — подготовка окружения (БД, серверы, доступы), в котором будет запускаться тестирование; обычно этим занимаются разработчики.
5. **Выполнение тестов** — непосредственный запуск тестов, фиксация и анализ найденных дефектов, повторный прогон после исправлений. Это итеративный этап — повторяется, пока дефекты не устранены.
6. **Завершение тестирования** — подготовка итогового отчёта, очистка тестовой среды, архивация сценариев, разбор полученного опыта.

На практике как разработчику мне важнее всего этапы 3 и 5 — подготовка тестовых данных и выполнение тестов — этим посвящены следующие уроки.

### Функциональное и нефункциональное тестирование

Все виды тестирования делятся на две большие группы:

- **функциональное тестирование** — проверяет, *что* делает система: соответствует ли её поведение требованиям (правильно ли функция считает, обрабатывает ли класс нужные случаи). Сюда относится и юнит-тестирование.
- **нефункциональное тестирование** — проверяет, *как* система это делает: производительность (нагрузочное тестирование), удобство использования (usability), безопасность, надёжность при масштабировании и т.д. Код при этом может работать правильно, но быть, например, слишком медленным или уязвимым.

Юнит-тестирование, которым мы будем заниматься в этом курсе, — это низкоуровневый вид **функционального** тестирования: он проверяет корректность работы конкретных изолированных единиц кода, а не системы в целом.

### Три категории тестовых данных

Хорошее покрытие функции всегда учитывает:

- **обычные случаи** — типичные корректные входы;
- **граничные случаи** — крайние допустимые значения (наименьшее/наибольшее из корректных);
- **некорректные случаи** — то, что функция не должна принимать, обычно проверяется через исключения.

Важный нюанс: то, что кажется "пограничным" по смыслу (например, ноль для функции, принимающей только положительные числа), может на деле быть **некорректным** случаем, а не граничным — если по условию задачи оно не входит в область допустимых значений вообще.

```python
def is_correct_grade(grade):
    if not isinstance(grade, int):
        raise TypeError('Оценка должна быть целым числом')
    if not 1 <= grade <= 5:
        return False
    return True

# обычные случаи: 2, 3, 4, а также любые числа < 1 или > 5, кроме границ
# граничные случаи: 1 и 5 (края корректного диапазона)
# некорректные случаи: любой не-int, например, '5' или 4.0
```

### Юнит-тестирование и подход "белого ящика"

Юнит-тестирование проверяет минимальные изолированные единицы приложения — функцию, метод, иногда целый класс или модуль, если он представляет собой логически цельное поведение. Это делается на ранних этапах разработки, чтобы не дать ошибке в одной единице «просочиться» в другие, которые от неё зависят.

Такой подход относится к стратегии **белого ящика**: тестировщик (в нашем случае — сам разработчик) видит внутреннюю реализацию и специально проверяет её детали — ветвления, циклы, граничные условия. Это противоположность **чёрному ящику**, где известны только вход и выход.

### Пирамида тестирования

Концептуальная модель, показывающая соотношение количества тестов разных уровней в проекте: чем ниже уровень (юнит-тесты) — тем больше тестов, чем выше (end-to-end/UI-тесты) — тем их меньше. Юнит-тесты — быстрые и дешёвые, поэтому их должно быть больше всего; они составляют основание пирамиды.

---

## 💡 Важные нюансы

- Полное покрытие всех возможных случаев обычно недостижимо — принцип «исчерпывающее тестирование невозможно».
- Успешное прохождение тестов **не гарантирует** отсутствие багов — только демонстрирует, что конкретные проверенные случаи работают верно.
- Юнит-тестирование — это база: если ошибка есть на этом уровне, она обычно «тянет» за собой сбои в других частях системы.
