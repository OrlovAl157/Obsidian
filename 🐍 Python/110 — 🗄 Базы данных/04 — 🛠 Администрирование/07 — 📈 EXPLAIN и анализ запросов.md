# 📈 EXPLAIN и анализ запросов

> `EXPLAIN` показывает **прогноз** оптимизатора — как MySQL планирует выполнить запрос. `EXPLAIN ANALYZE` реально **выполняет** запрос и показывает, что произошло на самом деле. План применим не только к индексам — его смотрят и для JOIN, подзапросов, GROUP BY.

## Справка

| Команда | Выполняет запрос? | Что показывает | С какой версии MySQL |
|---|---|---|---|
| `EXPLAIN` | нет | прогноз оптимизатора: план, оценка строк | всегда |
| `EXPLAIN ANALYZE` | да | реальный план **и** факт: время, число строк | 8.0.18+ |
| `EXPLAIN FORMAT=JSON` | нет | тот же прогноз, но детальнее, в JSON | 5.6+ |

| Поле в EXPLAIN | Значение | Хорошо / Плохо |
|---|---|---|
| `type = ALL` | полное сканирование таблицы | ❌ плохо на больших таблицах |
| `type = ref` | поиск по обычному индексу | ✅ хорошо |
| `type = const` | поиск по `PRIMARY KEY` / `UNIQUE` | ✅ лучшее |
| `key = NULL` | индекс не используется | ⚠️ |
| `rows` | оценка числа просматриваемых строк | чем меньше, тем лучше |
| `Extra: Using filesort` | требуется отдельная сортировка | ⚠️ |
| `Extra: Using temporary` | создаётся временная таблица | ⚠️ |

## 🔎 EXPLAIN — прогноз оптимизатора

`EXPLAIN` не выполняет запрос, а спрашивает у оптимизатора: «как бы ты это сделал?». Полезен, чтобы узнать, использует ли запрос индекс или идёт полное сканирование.

```sql
EXPLAIN SELECT * FROM Books WHERE author = 'Stephen King';

-- | id | select_type | table | type | possible_keys | key        | rows |
-- |  1 | SIMPLE      | Books | ref  | idx_author    | idx_author |  2   |
--                              ↑                      ↑
--                     использует индекс      применён этот индекс

-- Без индекса:
-- | id | select_type | table | type | possible_keys | key  | rows |
-- |  1 | SIMPLE      | Books | ALL  | NULL          | NULL |  5   |
--                              ↑                            ↑
--                     полное сканирование           все 5 строк
```

`rows` в обычном `EXPLAIN` — это **оценка**, посчитанная по статистике таблицы. Она может сильно отличаться от реального числа, особенно если статистика устарела.

## 🧭 EXPLAIN ANALYZE — реальное выполнение

`EXPLAIN ANALYZE` **выполняет** запрос по-настоящему и добавляет к плану реальные цифры: сколько времени заняла каждая операция и сколько строк было обработано на самом деле.

```sql
EXPLAIN ANALYZE
SELECT * FROM Books WHERE author = 'Stephen King';

-- -> Filter: (Books.author = 'Stephen King')
--     (cost=2.50 rows=2) (actual time=0.045..0.052 rows=2 loops=1)
--    -> Index lookup on Books using idx_author
--        (cost=2.50 rows=2) (actual time=0.040..0.046 rows=2 loops=1)
```

Что означают цифры:

| Обозначение | Смысл |
|---|---|
| `cost=2.50` | условная «стоимость» шага по оценке оптимизатора |
| `rows=2` | **прогноз** числа строк |
| `actual time=0.040..0.046` | реальное время первой и последней строки, мс |
| `rows=2` (в actual) | **фактическое** число строк |
| `loops=1` | сколько раз этот шаг выполнялся (важно внутри вложенных циклов JOIN) |

> ⚠️ Так как запрос реально выполняется, `EXPLAIN ANALYZE` **не подходит** для `INSERT`, `UPDATE`, `DELETE` в проде без осторожности — изменения будут внесены по-настоящему.

## ⚖️ EXPLAIN vs EXPLAIN ANALYZE

```
EXPLAIN          → «Как я СОБИРАЮСЬ это сделать?» (прогноз, без выполнения)
EXPLAIN ANALYZE  → «Как я РЕАЛЬНО это сделал?»    (факт, с выполнением)
```

> 💡 Аналогия: `EXPLAIN` — это маршрут в навигаторе до поездки («прогноз 20 минут»). `EXPLAIN ANALYZE` — реальная поездка с секундомером и счётчиком светофоров.

Главный сигнал для оптимизации — **расхождение прогноза и факта**:

```sql
EXPLAIN ANALYZE
SELECT * FROM Orders WHERE status = 'shipped';

-- (cost=100.00 rows=5000) (actual time=0.02..45.30 rows=50000 loops=1)
--                 ↑                                    ↑
--          прогноз: 5000 строк              факт: 50000 строк — в 10 раз больше
```

Такое расхождение обычно значит: устаревшая статистика таблицы (нужен `ANALYZE TABLE`) или неподходящий индекс.

```sql
ANALYZE TABLE Orders;   -- пересчитать статистику для оптимизатора
```

## 📦 EXPLAIN FORMAT=JSON

Даёт больше деталей, чем табличный вывод: точную стоимость каждого шага, использованные ключи, условия фильтрации.

```sql
EXPLAIN FORMAT=JSON
SELECT * FROM Books WHERE author = 'Stephen King';
```

```json
{
  "query_block": {
    "select_id": 1,
    "table": {
      "table_name": "Books",
      "access_type": "ref",
      "key": "idx_author",
      "rows_examined_per_scan": 2,
      "filtered": "100.00"
    }
  }
}
```

Полезен для сложных запросов с несколькими соединениями, где табличный вид читать неудобно.

## 🔗 План для JOIN, подзапросов и GROUP BY

`EXPLAIN` применяется не только к одиночным `SELECT` с фильтром — план строится для **всего запроса**.

**JOIN — порядок соединения таблиц:**

```sql
EXPLAIN SELECT *
FROM Books b
JOIN Authors a ON b.author_id = a.id
WHERE a.name = 'Stephen King';

-- | id | table | type | key         | rows |
-- |  1 | a     | ref  | idx_name    |   1  |   ← сначала Authors (меньше строк)
-- |  1 | b     | ref  | idx_author  |   3  |   ← потом Books
```

Порядок таблиц в выводе — это порядок, в котором MySQL реально их обходит, не обязательно совпадает с порядком в `FROM`/`JOIN`.

**Подзапрос — превращается ли в JOIN:**

```sql
EXPLAIN SELECT * FROM Books
WHERE author_id IN (SELECT id FROM Authors WHERE country = 'USA');

-- select_type = DEPENDENT SUBQUERY  → подзапрос выполняется для каждой строки ⚠️
-- select_type = SUBQUERY            → подзапрос выполняется один раз ✅
```

Подробнее о видах подзапросов — [[07 — 🔎 Подзапросы]].

**GROUP BY — сортировка и временные таблицы:**

```sql
EXPLAIN SELECT author_id, COUNT(*) FROM Books GROUP BY author_id;

-- Extra: Using temporary; Using filesort   ⚠️ группировка не через индекс
```

Если по полю `GROUP BY` есть индекс, `Using temporary` и `Using filesort` обычно исчезают.

## 💡 Практические замечания

- `EXPLAIN` и `EXPLAIN ANALYZE` работают перед **любым** запросом: `SELECT`, `UPDATE`, `DELETE` (с осторожностью для двух последних в `ANALYZE`)
- В `EXPLAIN` для `type` порядок от плохого к хорошему: `ALL` → `index` → `range` → `ref` → `eq_ref` → `const`
- Расхождение прогноза и факта — главный повод запустить `ANALYZE TABLE`
- `EXPLAIN ANALYZE` доступен с MySQL 8.0.18; в более старых версиях есть только обычный `EXPLAIN`
- Иногда полезно посмотреть на реальный план через `SHOW WARNINGS` сразу после `EXPLAIN` — там показывается переписанный (оптимизированный) SQL

## ⚠️ Частые ошибки

**❌ Запускать `EXPLAIN ANALYZE` на `DELETE`/`UPDATE` в проде «просто посмотреть».** Запрос выполнится по-настоящему, данные изменятся.

**❌ Доверять `rows` из обычного `EXPLAIN` как точному числу.** Это оценка по статистике, может быть далека от реальности — сверяй с `EXPLAIN ANALYZE`.

**❌ Игнорировать `key = NULL`, если `possible_keys` не пустой.** Значит, подходящий индекс есть, но оптимизатор решил его не использовать — стоит разобраться почему (например, из-за низкой селективности).

**❌ Не проверять план для `JOIN`, а только для одиночных `SELECT`.** Проблемы производительности чаще всего именно в порядке соединения и типе `type` у каждой из соединяемых таблиц.

---

## ✅ Главные правила

✅ `EXPLAIN` — прогноз без выполнения, `EXPLAIN ANALYZE` — реальное выполнение с фактами  
✅ Расхождение прогноза и факта → повод для `ANALYZE TABLE` или другого индекса  
✅ `EXPLAIN ANALYZE` на `UPDATE`/`DELETE` в проде — только с осторожностью, данные меняются по-настоящему  
✅ План строится для всего запроса: смотри `type` и `key` у каждой таблицы в `JOIN`  
✅ `Using temporary` / `Using filesort` в `Extra` — сигнал проверить индексы под `GROUP BY`/`ORDER BY`
