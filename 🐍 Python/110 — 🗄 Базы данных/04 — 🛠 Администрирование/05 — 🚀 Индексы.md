# 🚀 Индексы — памятка

> Индекс — структура данных которая ускоряет поиск записей в таблице. Работает как оглавление в книге: вместо просмотра всех страниц — сразу переходим к нужной. Плата — дополнительное место на диске и замедление записи.

## Справка

| Команда | Что делает |
|---|---|
| `CREATE INDEX idx ON t(col)` | создать обычный индекс |
| `CREATE UNIQUE INDEX idx ON t(col)` | создать уникальный индекс |
| `CREATE FULLTEXT INDEX idx ON t(col)` | создать полнотекстовый индекс |
| `CREATE INDEX idx ON t(col1, col2)` | создать составной индекс |
| `DROP INDEX idx ON t` | удалить индекс |
| `SHOW INDEX FROM t` | показать все индексы таблицы |
| `ALTER TABLE t RENAME INDEX old TO new` | переименовать индекс |
| `EXPLAIN SELECT ...` | показать план выполнения запроса |

## 📊 Общая схема

```
Без индекса — полное сканирование таблицы (Full Table Scan):
Books (10 000 строк)
│ WHERE author = 'Stephen King'
└── читает ВСЕ 10 000 строк → находит нужные

С индексом — поиск по B-tree:
INDEX(author)
│ WHERE author = 'Stephen King'
└── переходит сразу к нужным записям через дерево → читает только их

Цена индекса:
  ┌───────────────┬──────────┬────────────────────┐
  │               │ Без индекса │ С индексом       │
  ├───────────────┼──────────┼────────────────────┤
  │ SELECT (поиск)│ медленно │ быстро ✅          │
  │ INSERT        │ быстро   │ медленнее ⚠️       │
  │ UPDATE        │ быстро   │ медленнее ⚠️       │
  │ DELETE        │ быстро   │ медленнее ⚠️       │
  │ Место на диске│ меньше   │ больше ⚠️          │
  └───────────────┴──────────┴────────────────────┘
```

## 🟠 Кластеризованные и некластеризованные индексы

Все индексы в SQL делятся на два фундаментально разных вида — по тому, **как именно** они организуют доступ к данным.

**Кластеризованный индекс** определяет физический порядок хранения записей таблицы на диске. Записи с близкими ключевыми значениями физически лежат рядом друг с другом. Именно поэтому у таблицы может быть только **один** кластеризованный индекс — записи способны храниться лишь в одном порядке одновременно.

Кластеризованный индекс **не создаётся вручную** — он есть у любой таблицы автоматически. СУБД выбирает поле для него по такой логике:
1. Если у таблицы есть `PRIMARY KEY` — используется он
2. Если первичного ключа нет — берётся первое уникальное непустое (`NOT NULL UNIQUE`) поле
3. Если нет и такого — MySQL создаёт скрытое суррогатное целочисленное поле специально для этой цели

```
Таблица Books с PRIMARY KEY (id):

Физический порядок на диске = порядок по id
┌────┬─────────────────┬───────────────┐
│ id │ title           │ author        │
├────┼─────────────────┼───────────────┤
│ 1  │ Fight Club      │ Palahniuk     │  ← записи лежат
│ 2  │ The Green Mile  │ King          │    подряд по id
│ 3  │ It              │ King          │
└────┴─────────────────┴───────────────┘
```

Плотное хранение — одновременно и плюс, и минус: диапазонный поиск по первичному ключу (`WHERE id BETWEEN 10 AND 20`) выполняется очень быстро (бинарный поиск), но добавление или обновление записи может потребовать переупорядочивания части данных, что затратно по времени.

**Некластеризованный индекс** — это ровно то, что создаётся через `CREATE INDEX`. В отличие от кластеризованного, он хранится **отдельно от самой таблицы**, как самостоятельный объект. Внутри — только значения индексированного поля (в отсортированном виде) и ссылки на соответствующие записи таблицы:

```
Таблица Books (порядок по id, как в кластеризованном индексе)   Индекс idx_release_year (отдельная структура)
┌────┬─────────────────┬───────┬───────────────┐               ┌───────────────┬──────────────┐
│ id │ title           │ ...   │ release_year  │               │ release_year  │ → ссылка на  │
├────┼─────────────────┼───────┼───────────────┤               ├───────────────┼──────────────┤
│ 1  │ Fight Club      │ ...   │ 1996          │               │ 1954          │ → id 3, 5    │
│ 2  │ The Green Mile  │ ...   │ 1996          │               │ 1986          │ → id 4       │
│ 3  │ LOTR: Fellowship│ ...   │ 1954          │               │ 1996          │ → id 1, 2    │
└────┴─────────────────┴───────┴───────────────┘               │ 1999          │ → id 6       │
                                                                 └───────────────┴──────────────┘
```

Поскольку данные хранятся отдельно от таблицы и не диктуют физический порядок её строк, некластеризованных индексов на одной таблице можно создавать **сколько угодно** — в отличие от кластеризованного. Обратная сторона: чем больше полей включено в индекс, тем больше памяти он занимает, ведь индекс дублирует значения этих полей у себя.

## 🟢 Создание и удаление индексов

```sql
-- Создать индекс на одно поле
CREATE INDEX idx_author
ON Books(author);

-- Создать при создании таблицы
CREATE TABLE Books (
    id INT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(100) NOT NULL,
    author VARCHAR(100),
    price DECIMAL(10,2),
    INDEX idx_author (author),         -- обычный индекс
    INDEX idx_price (price)
);

-- Добавить индекс к существующей таблице
ALTER TABLE Books
ADD INDEX idx_author (author);

-- Просмотреть все индексы таблицы
SHOW INDEX FROM Books;
-- Поля вывода: Table, Key_name, Column_name, Non_unique, Cardinality

-- Удалить индекс
DROP INDEX idx_author ON Books;

-- Удалить через ALTER TABLE
ALTER TABLE Books
DROP INDEX idx_author;

-- Переименовать индекс
ALTER TABLE Books
RENAME INDEX idx_author TO idx_book_author;
```

## 🔵 Типы индексов

**Обычный INDEX — базовый:**

```sql
-- Ускоряет поиск, не накладывает ограничений на значения
CREATE INDEX idx_author ON Books(author);

-- Использование в запросах:
SELECT * FROM Books WHERE author = 'Stephen King';    -- ✅ использует индекс
SELECT * FROM Books ORDER BY author;                  -- ✅ использует индекс
SELECT * FROM Books JOIN Authors ON Books.author_id = Authors.id;  -- ✅ если есть индекс на author_id
```

**UNIQUE INDEX — уникальный:**

```sql
-- Запрещает дублирование значений в поле (как UNIQUE constraint)
CREATE UNIQUE INDEX idx_title ON Books(title);

-- При попытке вставить дубликат — ошибка
INSERT INTO Books (title, author, price) VALUES ('Fight Club', 'Other Author', 5.99);
-- ERROR 1062: Duplicate entry 'Fight Club' for key 'idx_title'
```

**FULLTEXT INDEX — полнотекстовый поиск:**

```sql
-- Для поиска по тексту — ищет слова внутри строки
CREATE FULLTEXT INDEX idx_title_search ON Books(title);

-- Использование — через MATCH...AGAINST
SELECT * FROM Books
WHERE MATCH(title) AGAINST('green mile');

-- Поиск в булевом режиме
SELECT * FROM Books
WHERE MATCH(title) AGAINST('+green -club' IN BOOLEAN MODE);
-- + обязательное слово, - исключённое слово
```

**Сравнение типов:**

| Тип | Дубликаты | Поиск по | Когда использовать |
|---|---|---|---|
| `INDEX` | ✅ разрешены | точное совпадение, диапазон | поля в WHERE, JOIN, ORDER BY |
| `UNIQUE INDEX` | ❌ запрещены | точное совпадение | уникальные поля (email, username) |
| `FULLTEXT` | ✅ разрешены | слова в тексте | поиск в длинных текстах |

## 🔴 Составной индекс

Индекс на несколько полей — ускоряет запросы с условием по нескольким столбцам:

```sql
-- Создать составной индекс
CREATE INDEX idx_author_price ON Books(author, price);

-- Эффективно для запросов которые используют ОБА поля:
SELECT * FROM Books WHERE author = 'King' AND price < 10;  -- ✅ использует индекс

-- Эффективно для запросов по ПЕРВОМУ полю:
SELECT * FROM Books WHERE author = 'King';                  -- ✅ использует индекс

-- НЕ эффективно если используется только второе поле:
SELECT * FROM Books WHERE price < 10;                       -- ❌ индекс не используется!
```

**Правило крайнего левого префикса:** составной индекс `(A, B, C)` работает для:
- `WHERE A = ...` ✅
- `WHERE A = ... AND B = ...` ✅
- `WHERE A = ... AND B = ... AND C = ...` ✅
- `WHERE B = ...` ❌ (нет A)
- `WHERE C = ...` ❌ (нет A и B)

## 🟡 Автоматические индексы

MySQL автоматически создаёт индексы для:

```sql
CREATE TABLE Books (
    id INT PRIMARY KEY,       -- ← автоматический PRIMARY KEY индекс
    title VARCHAR(100) UNIQUE,-- ← автоматический UNIQUE индекс
    author_id INT,
    FOREIGN KEY (author_id) REFERENCES Authors(id)  -- ← автоматический индекс
);

SHOW INDEX FROM Books;
-- Увидишь: PRIMARY на id, title на title, author_id на author_id
```

## 🟣 EXPLAIN — анализ запроса

`EXPLAIN` показывает план выполнения запроса — использует ли MySQL индекс или делает полное сканирование:

```sql
EXPLAIN SELECT * FROM Books WHERE author = 'Stephen King';

-- Вывод:
-- | id | select_type | table | type | possible_keys | key      | rows |
-- |  1 | SIMPLE      | Books | ref  | idx_author    | idx_author|  2  |
--                              ↑                      ↑
--                              ref = использует индекс  использован этот индекс

-- Без индекса:
-- | id | select_type | table | type | possible_keys | key  | rows |
-- |  1 | SIMPLE      | Books | ALL  | NULL          | NULL |  5   |
--                              ↑                            ↑
--                              ALL = полное сканирование    все 5 строк
```

**Ключевые поля в EXPLAIN:**

| Поле | Значение | Хорошо/Плохо |
|---|---|---|
| `type = ALL` | полное сканирование | ❌ плохо для больших таблиц |
| `type = ref` | использует индекс | ✅ хорошо |
| `type = const` | поиск по PRIMARY KEY | ✅ лучшее |
| `key = NULL` | индекс не используется | ⚠️ |
| `rows` | сколько строк просмотрено | чем меньше тем лучше |

## 📈 Сравнение производительности

Насколько именно ускоряет индекс — сильно зависит от объёма таблицы. На запросе вида `WHERE release_year = 1996` разница растёт вместе с количеством записей:

| Записей в таблице | Без индекса | С индексом |
|---|---|---|
| 1 000 | 0.0005 сек | 0.0003 сек |
| 10 000 | 0.0016 сек | 0.0006 сек |
| 100 000 | 0.015 сек | 0.003 сек |
| 1 000 000 | 0.15 сек | 0.03 сек |

Без индекса СУБД сканирует таблицу от первой записи до последней (`type = ALL` в `EXPLAIN`) — время растёт линейно с числом строк. С индексом СУБД находит нужное значение в дереве за несколько шагов и сразу переходит к записям — рост времени намного медленнее. Чем больше таблица, тем заметнее выигрыш: на 1000 строк разница в разы, на миллионе — уже на порядок.

## 💡 Когда создавать и не создавать

**Создавать индекс:**

```sql
-- ✅ Поля которые часто в WHERE
WHERE author = 'King'        → CREATE INDEX ON Books(author)

-- ✅ Поля которые часто в JOIN
JOIN Authors ON Books.author_id = Authors.id  → INDEX ON Books(author_id)

-- ✅ Поля которые часто в ORDER BY
ORDER BY price               → CREATE INDEX ON Books(price)

-- ✅ Поля с высокой уникальностью (email, username, id)
WHERE email = 'user@test.com' → UNIQUE INDEX ON users(email)
```

**Не создавать индекс:**

```sql
-- ❌ Маленькие таблицы (< 1000 строк) — полное сканирование быстрее
-- ❌ Поля с низкой уникальностью (статус: 'active'/'inactive', пол)
-- ❌ Поля которые редко используются в запросах
-- ❌ Таблицы с очень частой записью (INSERT/UPDATE/DELETE замедлятся)
-- ❌ Слишком много индексов на одной таблице — замедляют запись
```

## ⚠️ Частые ошибки

**❌ Индекс только на второе поле составного:**
```sql
CREATE INDEX ON Books(author, price);
SELECT * FROM Books WHERE price < 10;  -- ❌ индекс не используется!
-- Создай отдельный индекс если нужен только price:
CREATE INDEX ON Books(price);  -- ✅
```

**❌ Слишком много индексов:**
```sql
-- На таблице с частыми INSERT:
CREATE INDEX idx1 ON Books(author);
CREATE INDEX idx2 ON Books(price);
CREATE INDEX idx3 ON Books(title);
CREATE INDEX idx4 ON Books(amount);
-- При каждом INSERT MySQL обновляет ВСЕ индексы → медленно!
```

**❌ FULLTEXT вместо обычного для точного поиска:**
```sql
-- FULLTEXT для поиска по словам, не для точного совпадения
CREATE FULLTEXT INDEX ON Books(author);
SELECT * FROM Books WHERE author = 'King';  -- лучше обычный INDEX!
```

## ✅ Главные правила

✅ Индекс ускоряет `SELECT` но замедляет `INSERT/UPDATE/DELETE`  
✅ Кластеризованный индекс — один на таблицу, определяет физический порядок хранения, создаётся автоматически  
✅ Некластеризованный индекс — сколько угодно на таблицу, хранится отдельно, содержит ссылки на записи  
✅ `PRIMARY KEY` и `UNIQUE` создают индексы автоматически  
✅ Индексируй поля которые часто в `WHERE`, `JOIN`, `ORDER BY`  
✅ Составной индекс работает по правилу крайнего левого префикса  
✅ `EXPLAIN` — всегда проверяй использует ли запрос индекс  
✅ `FULLTEXT` — для поиска слов в тексте, не для точного совпадения  
✅ Не создавай индексы на маленьких таблицах и полях с низкой уникальностью  
✅ `SHOW INDEX FROM t` — просмотреть все индексы таблицы
