# 📜 Транзакции в процедурах

> Транзакцией можно управлять прямо внутри хранимой процедуры MySQL: проверить результат операций, откатить всё через `ROLLBACK` или только часть через `SAVEPOINT`, перехватить ошибку обработчиком исключений.

## Справка

| Версия `ADD_ORDER` | Что добавляет | Когда откат |
|---|---|---|
| 1 | `START TRANSACTION` … `COMMIT` | никогда, проверок нет |
| 2 | `IF (SELECT quantity ...) < 0` → `ROLLBACK`, иначе `COMMIT` | остаток стал отрицательным |
| 3 | `CHECK` + `CONTINUE HANDLER` + `SAVEPOINT` | ошибка ограничения → `ROLLBACK TO add_user` |

| Элемент | Синтаксис | Смысл |
|---|---|---|
| Ограничение | `quantity INT CHECK (quantity >= 0)` | ошибка при отрицательном значении |
| Обработчик | `DECLARE CONTINUE HANDLER FOR SQLEXCEPTION действие` | при ошибке выполнить действие и **продолжить** |
| Обработчик | `DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ... END` | при ошибке выполнить действие и **выйти** из блока |
| Флаг ошибки | `DECLARE is_negative INT DEFAULT 0` | локальная переменная-признак ошибки |
| Частичный откат | `SAVEPOINT имя` / `ROLLBACK TO имя` | вернуться к точке, транзакция остаётся открытой |

| Вызов | Результат |
|---|---|
| `CALL ADD_ORDER(5, 'Thomas Hanks', 2)` | остаток 1 → недостаточно, изменений нет |
| `CALL ADD_ORDER(5, 'Thomas Hanks', 1)` | остаток `1 → 0`, аренда записана |
| `CALL ADD_ORDER(5, 'Michael Clarke Duncan', 2)` (версия 3) | `Books` и `BooksRental` без изменений, пользователь **добавлен** |

## 🧩 Зачем транзакции в процедурах

Интерактивно мы видим результат каждого запроса и сами решаем: `COMMIT` или `ROLLBACK`. В реальных приложениях решение принимает **код**: драйвер или библиотека языка предоставляют методы начала, подтверждения и отката, а ошибки ловятся средствами языка. Под капотом это те же `START TRANSACTION`, `COMMIT`, `ROLLBACK`.

В MySQL ту же логику можно вынести **внутрь БД** — в хранимую процедуру.

Пример — процедура `ADD_ORDER(book, username, amount)`: создаёт запись об аренде и уменьшает `quantity` книги. Схема БД — та же, что в [[03 — 🔄 Транзакции в MySQL]] (`Authors`, `Books`, `Users`, `BooksRental`).

---

## 🧱 Версия 1 — без проверки

```sql
DELIMITER //
CREATE PROCEDURE ADD_ORDER(book INT, username TEXT, amount INT)
BEGIN
    START TRANSACTION;
        INSERT INTO BooksRental (book_id, user_id, quantity)
        SELECT book, id, amount
        FROM Users
        WHERE user = username;

        UPDATE Books
        SET quantity = quantity - amount
        WHERE id = book;
    COMMIT;
END //
DELIMITER ;
```

Транзакция завершается успешно, но логика **некорректна**: книга 5 есть в одном экземпляре, и если взять две, заказ создастся, а остаток станет `-1`.

> 💡 Отсутствие SQL-ошибки ≠ корректный результат. Согласованность (**C** из ACID) надо проверять самим — [[01 — 🔄 Транзакции и ACID]].

## 🛡 Версия 2 — проверка и ROLLBACK

После обновления проверяем остаток: если он отрицательный — откат, иначе фиксация.

```sql
DELIMITER //
CREATE PROCEDURE ADD_ORDER(book INT, username TEXT, amount INT)
BEGIN
    START TRANSACTION;
        INSERT INTO BooksRental (book_id, user_id, quantity)
        SELECT book, id, amount
        FROM Users
        WHERE user = username;

        UPDATE Books
        SET quantity = quantity - amount
        WHERE id = book;

        -- Проверяем остаток
        IF (SELECT quantity
            FROM Books
            WHERE id = book) < 0 THEN
            ROLLBACK;      -- недостаточно книг: откат
        ELSE
            COMMIT;        -- достаточно: фиксируем
        END IF;
END //
DELIMITER ;
```

```sql
CALL ADD_ORDER(5, 'Thomas Hanks', 2);
-- → Books и BooksRental не изменились (остаток был бы -1, всё откатили)

CALL ADD_ORDER(5, 'Thomas Hanks', 1);
-- → Haunted: quantity 1 → 0, в BooksRental добавлена аренда, COMMIT
```

Обе ветки `IF` **завершают** транзакцию: и `ROLLBACK`, и `COMMIT`.

## 🪤 Версия 3 — обработчик исключений и SAVEPOINT

Пусть на поле `quantity` наложено ограничение — отрицательные значения запрещены:

```sql
CREATE TABLE Books
(
    ...
    quantity INT CHECK (quantity >= 0)
);
```

Теперь `UPDATE`, уводящий остаток в минус, вызывает **ошибку**. Чтобы её перехватить, объявляем обработчик, а чтобы откатить только часть работы, ставим точку сохранения.

```sql
DELIMITER //
CREATE PROCEDURE ADD_ORDER(book INT, username TEXT, amount INT)
BEGIN
    DECLARE is_negative INT DEFAULT 0;                       -- флаг ошибки
    DECLARE CONTINUE HANDLER FOR SQLEXCEPTION SET is_negative := 1;

    START TRANSACTION;
        IF username NOT IN (SELECT user FROM Users) THEN     -- нового пользователя добавляем
            INSERT INTO Users (user)
            VALUES (username);
        END IF;

        SAVEPOINT add_user;                                  -- точка сохранения

        INSERT INTO BooksRental (book_id, user_id, quantity)
        SELECT book, id, amount
        FROM Users
        WHERE user = username;

        UPDATE Books
        SET quantity = quantity - amount
        WHERE id = book;                                     -- ошибка CHECK → is_negative = 1

        IF is_negative THEN
            ROLLBACK TO add_user;                            -- откат до точки, не дальше
        END IF;
    COMMIT;
END //
DELIMITER ;
```

```sql
CALL ADD_ORDER(5, 'Michael Clarke Duncan', 2);
-- → Books и BooksRental без изменений: остаток не позволяет
-- → Users: пользователь добавлен (он был до SAVEPOINT и остался)
```

**Как это работает:**

1. `DECLARE CONTINUE HANDLER` — при любой SQL-ошибке выполнить `SET is_negative := 1` и **продолжить** процедуру
2. Пользователь добавляется до `SAVEPOINT`
3. `INSERT` в `BooksRental` проходит, `UPDATE` нарушает `CHECK` → ошибка → флаг `is_negative = 1`
4. `IF is_negative` → `ROLLBACK TO add_user`: аренда отменена, пользователь остался
5. `COMMIT` завершает транзакцию (`ROLLBACK TO` её не закрывает)

> 💡 Вариант с `EXIT HANDLER` (сам делает `ROLLBACK` и выходит из процедуры) — процедура `SAFE_DELETE` в [[06 — 📜 Процедуры]].

## 💡 Практические замечания

- Транзакции должны быть как можно **короче**: чем дольше транзакция, тем выше вероятность блокировок и конфликтов
- В процедурах начинать транзакцию нужно только через `START TRANSACTION`: `BEGIN` здесь означает начало блока
- Порядок в начале блока: сначала `DECLARE` переменных, потом `DECLARE` обработчиков, потом операторы — см. [[07 — 🧮 Переменные]]
- `CHECK` реально работает с MySQL **8.0.16**; в более старых версиях ограничение принимается, но игнорируется
- Версия 2 проверяет результат **вручную** (`IF ... < 0`), версия 3 опирается на **ограничение БД** и перехват ошибки

## ⚠️ Частые ошибки

**❌ Ветка, где транзакция не завершена.** Если `IF` откатывает, а в `ELSE` нет `COMMIT`, транзакция останется открытой.

**❌ `BEGIN` вместо `START TRANSACTION` внутри процедуры.** MySQL воспримет его как блок, а не начало транзакции.

**❌ `DECLARE ... HANDLER` после обычных операторов.** Все `DECLARE` — в самом начале блока.

**❌ `CONTINUE HANDLER` без проверки флага.** Ошибка перехвачена, процедура пошла дальше, и если флаг не проверить, ошибка останется незамеченной, а данные — частично изменёнными.

**❌ `ROLLBACK TO` без `COMMIT` после него.** Транзакция остаётся открытой.

**❌ DDL внутри транзакции в процедуре.** `CREATE`, `ALTER`, `DROP` неявно фиксируют всё сделанное.

---

## ✅ Главные правила

✅ Успешный запрос ≠ корректный результат: проверяй условия и откатывай  
✅ Каждая ветка процедуры должна завершать транзакцию: `COMMIT` или `ROLLBACK`  
✅ В процедурах — `START TRANSACTION`, не `BEGIN`  
✅ `CONTINUE HANDLER` + флаг ошибки: обязательно проверяй флаг  
✅ `SAVEPOINT` + `ROLLBACK TO` — частичный откат, потом всё равно `COMMIT`  
✅ `DECLARE` (переменные, потом обработчики) — в начале блока  
✅ Транзакции — короткие
