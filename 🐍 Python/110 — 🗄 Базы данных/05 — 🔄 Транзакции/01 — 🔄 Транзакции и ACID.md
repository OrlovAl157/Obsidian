# 🔄 Транзакции и ACID

> Транзакция — набор операций с БД, который выполняется как единое целое по принципу «всё или ничего». ACID — четыре требования, которые делают транзакции надёжными.

## Справка

| Буква | Свойство | Суть | Пример (перевод денег) |
|---|---|---|---|
| **A** | Atomicity — атомарность | всё или ничего | сбой после списания → списание отменяется |
| **C** | Consistency — согласованность | БД переходит из одного корректного состояния в другое | сумма списанного = сумме зачисленного |
| **I** | Isolation — изоляция | параллельные транзакции не мешают друг другу | другой перевод не видит промежуточный баланс |
| **D** | Durability — устойчивость | после подтверждения данные не пропадут даже при сбое | перезагрузка сервера не отменяет проведённый перевод |

| Проблема | Причина | Чем решается |
|---|---|---|
| Конкурентный доступ | несколько пользователей меняют одни данные одновременно | изоляция (**I**) |
| Целостность данных | сбой между логически связанными операциями | атомарность (**A**), согласованность (**C**), устойчивость (**D**) |

## 🎯 Зачем нужны транзакции

Если в момент запроса что-то пойдёт не так (два пользователя меняют одни данные, приложение упало, сервер перезагрузился), данные могут оказаться в **несогласованном (неконсистентном)** состоянии: «висящие» заказы, дубли, потерянные деньги.

### 🏃 Проблема конкурентного доступа

Много пользователей работают одновременно, и между запросами одного из них могут вклиниться запросы других. Если операции логически связаны, чужие изменения «посередине» дают неверный результат.

```
Остаток товара = 1. Два покупателя одновременно:

Покупатель A: проверил остаток (1) ─────────► купил, остаток = 0
Покупатель B: проверил остаток (1) ─────────► купил, остаток = 0
                                              ❌ продано 2, а товар один
```

```
Баланс = 1000. Два процесса списывают по 1000:

Процесс 1: прочитал 1000 ──► списал 1000
Процесс 2: прочитал 1000 ──► списал 1000
                              ❌ баланс отрицательный
```

### 💥 Проблема целостности данных

Даже у одного пользователя сбой посреди цепочки операций ломает данные.

| Сценарий | Операции | Что будет при сбое посередине |
|---|---|---|
| Заказ в магазине | 1. создать заказ → 2. уменьшить остаток → 3. записать в историю | заказ есть, товар не зарезервирован |
| Перевод денег | 1. списать с первого счёта → 2. зачислить на второй | деньги списаны, но не дошли |

Обе проблемы решаются **транзакциями**.

## 📦 Что такое транзакция

**Транзакция** — последовательность операций, которые выполняются как единое целое: либо выполнились **все**, либо **ни одна**.

> 💡 Аналогия: банкомат. «Выдать наличные» и «списать сумму со счёта» — две операции. Если банкомат выдал деньги, а баланс не уменьшил (или наоборот), это ошибка. Правильно — либо обе операции, либо ни одной.

```sql
-- Перевод 500 со счёта 1 на счёт 2
START TRANSACTION;

UPDATE Accounts SET balance = balance - 500 WHERE id = 1;  -- списали
UPDATE Accounts SET balance = balance + 500 WHERE id = 2;  -- зачислили

COMMIT;  -- → оба изменения зафиксированы
```

Если на любом шаге ошибка, вместо `COMMIT` выполняется `ROLLBACK`, и БД возвращается к состоянию **до** транзакции.

## 🧪 ACID

**ACID** — набор требований к транзакционной системе, обеспечивающих её надёжную и предсказуемую работу. Аббревиатура из первых букв английских названий.

### 🅰️ Atomicity — атомарность

Транзакция — неделимая единица. Не бывает состояния «частично выполнена»: результат фиксируется, только когда корректно выполнены **все** инструкции.

- Перевод денег: сбой после списания, но до зачисления → транзакция отменяется целиком
- Заказ: запись о заказе создана, а остаток уменьшить не удалось → записи о заказе в БД не будет

### 🅲 Consistency — согласованность

Транзакция переводит БД из одного согласованного состояния в другое. Все правила и ограничения соблюдаются, данные не противоречат друг другу.

Согласованность задают **ограничения БД** (`CHECK`, `FOREIGN KEY`, `UNIQUE`) и **бизнес-логика приложения**:

- при переводе сумма списанного всегда равна сумме зачисленного, а баланс не уходит в минус
- заказ не может быть оформлен без уменьшения остатка на складе

### 🅸 Isolation — изоляция

Транзакции выполняются независимо. В идеале изменения одной не видны другим, пока она не завершена.

> ⚠️ Полная изоляция дорогая (замедляет систему), поэтому существуют **уровни изоляции** — компромисс между скоростью и надёжностью. Подробнее — [[02 — 🔒 Изоляция транзакций]].

### 🅳 Durability — устойчивость

После завершения транзакции изменения сохраняются **навсегда**, даже при сбое системы. Данные фиксируются в энергонезависимой памяти, и БД восстанавливается до последнего успешного состояния без потерь.

## 🔁 Жизненный цикл транзакции

```
START TRANSACTION
      │
      ▼
 операция 1 ──► операция 2 ──► операция 3
      │
      ├── всё успешно ──────► COMMIT   → изменения зафиксированы навсегда
      │
      └── ошибка / отмена ──► ROLLBACK → БД вернулась к исходному состоянию
```

```sql
START TRANSACTION;
-- операции
COMMIT;    -- → зафиксировать

START TRANSACTION;
-- операции
ROLLBACK;  -- → отменить всё, что было после START TRANSACTION
```

Синтаксис и особенности в MySQL — в [[03 — 🔄 Транзакции в MySQL]].

## 💡 Практические замечания

- Транзакция ≠ один запрос. Это **группа логически связанных** операций
- Атомарность, согласованность и устойчивость защищают от сбоев, изоляция — от конкурентного доступа
- Согласованность обеспечивается не только СУБД: без ограничений в схеме и проверок в логике «согласованное состояние» никто не гарантирует
- Транзакции должны быть **как можно короче**: чем дольше транзакция, тем выше риск блокировок и конфликтов
- Приложения обычно управляют транзакциями через драйвер или библиотеку языка — под капотом это те же `START TRANSACTION`, `COMMIT`, `ROLLBACK`
- Транзакции поддерживают не все движки хранения: в MySQL это **InnoDB**

## ⚠️ Частые ошибки

**❌ Считать, что СУБД сама обеспечит согласованность:**
```sql
-- В таблице нет ограничения на quantity
UPDATE Books SET quantity = quantity - 5 WHERE id = 5;
-- → quantity = -4, транзакция «успешна», но данные бессмысленны
```
✅ Добавить `CHECK (quantity >= 0)` или проверку в процедуре с `ROLLBACK`.

**❌ Выполнять связанные операции без транзакции:**
```sql
UPDATE Accounts SET balance = balance - 500 WHERE id = 1;
-- ❌ сбой здесь: деньги списаны, но не зачислены
UPDATE Accounts SET balance = balance + 500 WHERE id = 2;
```
✅ Обернуть обе операции в `START TRANSACTION ... COMMIT`.

**❌ Держать транзакцию открытой «на всякий случай»:** блокирует строки для других пользователей.

---

## ✅ Главные правила

✅ Транзакция — «всё или ничего»  
✅ **A** — нет частично выполненных транзакций  
✅ **C** — БД всегда переходит из корректного состояния в корректное (ограничения + логика приложения)  
✅ **I** — параллельные транзакции не должны влиять друг на друга (степень настраивается уровнем изоляции)  
✅ **D** — подтверждённое (`COMMIT`) не пропадает при сбое  
✅ Логически связанные операции — в одну транзакцию  
✅ Транзакции — короткие
