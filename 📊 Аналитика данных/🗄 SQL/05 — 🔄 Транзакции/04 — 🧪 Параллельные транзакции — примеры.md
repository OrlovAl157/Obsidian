## Справка

Исходные данные — отдельная учебная таблица `Books` (не путать со схемой из [[03 — 🔄 Транзакции в MySQL]]):

| id | title | author | price |
|---|---|---|---|
| 1 | The Shining | Stephen King | 7.99 |
| 2 | Fight Club | Chuck Palahniuk | 9.99 |
| 3 | The Catcher in the Rye | J.D. Salinger | 3.49 |
| 4 | The Green Mile | Stephen King | 15.99 |
| 5 | Haunted | Chuck Palahniuk | 13.99 |

| № | Сценарий | Уровень | Результат |
|---|---|---|---|
| 1 | обе транзакции меняют одну строку | по умолчанию | T2 **ждёт** COMMIT от T1 |
| 2 | T2 читает строку, изменённую T1 (не зафиксировано) | `REPEATABLE READ` | T2 видит **старое** значение `3.49` |
| 3 | то же, но T2 на `READ UNCOMMITTED` | `READ UNCOMMITTED` | **грязное чтение** `7.19` |
| 4 | T1 читает строку дважды, между чтениями T2 её меняет | `READ COMMITTED` | **неповторяющееся чтение** `9.99 → 19.99` |
| 5 | как № 4, но по умолчанию | `REPEATABLE READ` | оба чтения `15.99` |
| 6 | T1 дважды выбирает `price > 10`, между выборками T2 вставляет строку | `READ COMMITTED` | **фантом**: 2 строки → 3 |
| 7 | T2 вставляет строку под условие выборки T1 | `SERIALIZABLE` | INSERT T2 **ждёт** COMMIT от T1 |
| 8 | read-modify-write через переменную | по умолчанию | **потерянное обновление** |
| 9 | перекрёстные UPDATE двух строк | по умолчанию | **deadlock**, ошибка 1213 |

## 🧰 Как воспроизвести

- открой **два подключения** к одной БД (два окна клиента), T1 и T2
- выполняй шаги строго по порядку из схемы
- `SET TRANSACTION ISOLATION LEVEL ...` ставь **до** `START TRANSACTION`: только тогда настройка сработает (см. [[03 — 🔄 Транзакции в MySQL]])
- текущий уровень: `SELECT @@transaction_isolation;`
- после экспериментов верни данные в исходное состояние

Схемы ниже — в две колонки: слева T1, справа T2, по времени сверху вниз.

## 🔐 Блокировка строки при записи

### 1️⃣ Две транзакции меняют одну строку

```
T1                                    T2
START TRANSACTION;
UPDATE Books SET price = price + 5
WHERE id = 1;
                                      START TRANSACTION;
                                      UPDATE Books SET price = price + 5
                                      WHERE id = 1;    -- ⏳ ждёт T1
COMMIT;
                                      -- → UPDATE выполняется
                                      COMMIT;
```

**Почему:** T1 заблокировала строку `id = 1`. СУБД не допускает одновременного изменения одной строки разными транзакциями, T2 «зависает» до `COMMIT` или `ROLLBACK` у T1.

**Итог:** цена `7.99 → 12.99 → 17.99`, обе прибавки учтены.

---

## 🧟 Грязное чтение

### 2️⃣ Читаем строку, которую T1 изменила, но не зафиксировала (`REPEATABLE READ`)

```
T1                                    T2
START TRANSACTION;
UPDATE Books SET price = price + 5
WHERE id = 3;
                                      START TRANSACTION;
                                      SELECT price FROM Books
                                      WHERE id = 3;
                                      -- → 3.49
                                      COMMIT;
COMMIT;
```

**Почему:** на уровне по умолчанию транзакция видит только то, что было зафиксировано на момент её начала. Незавершённые изменения T1 для T2 не существуют, **грязного чтения нет**.

### 3️⃣ То же на `READ UNCOMMITTED`

```
T1                                    T2
START TRANSACTION;
UPDATE Books SET price = price * 0.9
WHERE id = 1;
                                      SET TRANSACTION ISOLATION LEVEL
                                          READ UNCOMMITTED;
                                      START TRANSACTION;
                                      SELECT * FROM Books WHERE id = 1;
                                      -- → price = 7.19  ❌ грязное чтение
                                      COMMIT;
ROLLBACK;                             -- цена снова 7.99
```

**Почему:** самый низкий уровень разрешает читать чужие незафиксированные изменения. T2 увидела `7.19`, которого после `ROLLBACK` никогда не существовало.

**Как решить:** уровень `READ COMMITTED` или выше.

> ⚠️ В исходном уроке перед `WHERE id = 1` стояла лишняя `;`. С ней запрос не выполнится.

---

## 🔀 Неповторяющееся чтение

### 4️⃣ Одна строка, два чтения, `READ COMMITTED`

```
T1                                    T2
SET TRANSACTION ISOLATION LEVEL
    READ COMMITTED;
START TRANSACTION;
SELECT price FROM Books WHERE id = 2;
-- → 9.99
                                      START TRANSACTION;
                                      UPDATE Books SET price = price + 10
                                      WHERE id = 2;
                                      COMMIT;
SELECT price FROM Books WHERE id = 2;
-- → 19.99  ❌ неповторяющееся чтение
COMMIT;
```

**Почему:** на `READ COMMITTED` каждое чтение видит все данные, зафиксированные к моменту **этого** чтения. Между двумя `SELECT` T2 зафиксировала изменение, и один и тот же запрос дал разные значения.

**Как решить:** `REPEATABLE READ` или `SERIALIZABLE`.

### 5️⃣ То же на `REPEATABLE READ` (по умолчанию)

```
T1                                    T2
START TRANSACTION;
SELECT price FROM Books WHERE id = 4;
-- → 15.99
                                      START TRANSACTION;
                                      UPDATE Books SET price = price + 20
                                      WHERE id = 4;
                                      COMMIT;
SELECT price FROM Books WHERE id = 4;
-- → 15.99  ✅ то же значение
COMMIT;
```

**Почему:** T1 работает со снимком данных на момент первого чтения. Чужие зафиксированные изменения она в рамках своей транзакции не видит, пока не завершится.

## 👻 Фантомное чтение

### 6️⃣ Новая строка между двумя выборками (`READ COMMITTED`)

```
T1                                    T2
SET TRANSACTION ISOLATION LEVEL
    READ COMMITTED;
START TRANSACTION;
SELECT * FROM Books WHERE price > 10;
-- → id 4 (15.99), id 5 (13.99)
                                      START TRANSACTION;
                                      INSERT INTO Books (title, author, price)
                                      VALUES ('Doctor Sleep',
                                              'Stephen King', 25.00);
                                      COMMIT;
SELECT * FROM Books WHERE price > 10;
-- → id 4, id 5, id 6 (25.00)  ❌ фантом
COMMIT;
```

**Почему:** между двумя одинаковыми выборками изменился **набор строк**: T2 добавила подходящую под условие запись.

**Как решить (по уроку):** `SERIALIZABLE`.

> 💡 Нюанс InnoDB: на `REPEATABLE READ` обычный `SELECT` читает снимок, и такой фантом в нём обычно не виден. Проверь экспериментом: повтори сценарий без `SET TRANSACTION`. См. [[02 — 🔒 Изоляция транзакций]].

### 7️⃣ Вставка под условие выборки (`SERIALIZABLE`)

```
T1                                    T2
SET TRANSACTION ISOLATION LEVEL
    SERIALIZABLE;
START TRANSACTION;
SELECT * FROM Books WHERE price > 10;
                                      START TRANSACTION;
                                      INSERT INTO Books (title, author, price)
                                      VALUES ('The Institute',
                                              'Stephen King', 22.00);
                                      -- ⏳ ждёт T1
COMMIT;
                                      -- → INSERT выполняется
                                      COMMIT;
```

**Почему:** на `SERIALIZABLE` MySQL блокирует **диапазон** строк, который мог повлиять на результат выборки. Добавлять, менять и удалять такие строки другие транзакции не могут, пока T1 не завершится.

## 🕳 Потерянное обновление

### 8️⃣ Read-modify-write через переменную

```
T1                                    T2
START TRANSACTION;                    START TRANSACTION;
                                      SELECT price INTO @tmp_price
                                      FROM Books WHERE id = 1;
                                      -- @tmp_price = 7.99
UPDATE Books SET price = price + 5
WHERE id = 1;
COMMIT;                               -- в БД теперь 12.99
                                      UPDATE Books
                                      SET price = @tmp_price + 10
                                      WHERE id = 1;
                                      COMMIT;
-- → price = 17.99  ❌ ожидалось 22.99 (7.99 + 5 + 10)
```

**Почему:** T2 вычислила новое значение по **устаревшей копии** цены (`7.99`) и затёрла результат T1. Прибавка `+5` потеряна.

**Как решить:**

```sql
-- ✅ атомарное обновление: чтение и запись в одной операции
UPDATE Books SET price = price + 10 WHERE id = 1;

-- ✅ или блокировка строки до конца транзакции
SELECT price INTO @tmp_price FROM Books WHERE id = 1 FOR UPDATE;
```

> ⚠️ **Не проверено.** Урок показывает этот сценарий на `SERIALIZABLE` и утверждает, что потерянное обновление остаётся. В InnoDB на этом уровне обычный `SELECT` внутри транзакции превращается в блокирующее чтение (`FOR SHARE`), поэтому вместо потери возможны ожидание или deadlock. На уровне по умолчанию сценарий работает как на схеме выше. Проверь оба уровня экспериментом.

## 💀 Взаимная блокировка

### 9️⃣ Перекрёстные обновления двух строк

```
T1                                    T2
START TRANSACTION;
UPDATE Books SET price = price + 1
WHERE id = 1;                         -- T1 держит строку 1
                                      START TRANSACTION;
                                      UPDATE Books SET price = price + 1
                                      WHERE id = 2;   -- T2 держит строку 2
UPDATE Books SET price = price + 1
WHERE id = 2;                         -- ⏳ T1 ждёт T2
                                      UPDATE Books SET price = price + 1
                                      WHERE id = 1;   -- ⏳ T2 ждёт T1 → 💀
```

**Результат:** MySQL обнаруживает deadlock и принудительно завершает **одну** транзакцию (жертву):

```
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

Жертва откатывается, вторая транзакция продолжает работу.

**Как избежать:**

- обращаться к строкам в **одном и том же порядке** во всех транзакциях
- делать транзакции короткими
- в приложении **перезапускать** транзакцию после ошибки 1213

## 💡 Практические замечания

- Все примеры — для MySQL. В других СУБД поведение может отличаться: реализация изоляции, блокировок и многоверсионности своя
- Причину последнего deadlock можно посмотреть в `SHOW ENGINE INNODB STATUS` (раздел `LATEST DETECTED DEADLOCK`)
- Если T1 «забыла» завершиться, T2 ждёт ограниченное время и получает `ERROR 1205: Lock wait timeout exceeded` (по умолчанию около 50 секунд)
- Лучший способ понять изоляцию: самому менять порядок операций и уровни

## ⚠️ Частые ошибки

**❌ `SET TRANSACTION` после `START TRANSACTION`.** Получишь ошибку 1568, а эксперимент пойдёт на уровне по умолчанию.

**❌ Забыть `COMMIT` или `ROLLBACK` в одном из окон.** Оставшаяся открытой транзакция держит блокировки, и другое окно «зависает».

**❌ Судить об аномалии по одному подключению.** Для воспроизведения всегда нужны два независимых соединения.

**❌ Не вернуть данные после эксперимента.** Следующий сценарий начнётся с «испорченных» цен.

---

## ✅ Главные правила

✅ Запись в одну строку блокирует других писателей до `COMMIT`/`ROLLBACK`  
✅ `REPEATABLE READ` (по умолчанию) не даёт ни грязного, ни неповторяющегося чтения  
✅ `READ UNCOMMITTED` — грязное чтение, `READ COMMITTED` — неповторяющееся чтение и фантомы  
✅ `SERIALIZABLE` блокирует диапазон, вставка под условие чужой выборки ждёт  
✅ Read-modify-write через переменную даёт потерянное обновление на уровне по умолчанию, лечится атомарным `UPDATE` или `FOR UPDATE`  
✅ Deadlock — штатная ситуация: MySQL откатит одну транзакцию, приложение должно повторить  
✅ `SET TRANSACTION` — строго до `START TRANSACTION`
